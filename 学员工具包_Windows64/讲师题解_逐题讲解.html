01 · 没有扩展名的图片

本题任务

附件为 01_file/unknown.dat。识别它的真实格式，找到隐藏信息并提交 flag，同时说明编码值来自哪里。

解题思路：为什么从这里开始

题目先问“真实格式”，因此第一步要验证文件内容，不能由 .dat 猜用途。确认 PNG 后，优先检查格式本来就能保存的文字字段；这比没有线索地枚举隐写参数更直接。只有在 Comment 中实际发现可疑编码值后，才提出“它可能是 Base64”的假设。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
先识别格式：finspect type 与 xxd识别器给出候选，十六进制视图让你亲眼核对签名；改后缀不会改变字节。开头符合 PNG 签名，后面还有可解析的 IHDR，才沿图片路线继续。
再读元数据：exiftool -a -u -G1PNG 不只保存像素，还能包含文本。先查看字段组、字段名和原值，避免漏掉经过编码的线索。发现 Comment 中的长串，而不是假定“任意长串都是答案”。
定向提取：exiftool -b -Comment这一条只取字段值，避免将标签名、冒号等显示文字混入解码输入。得到完整原串，保留其来源为此文件的 Comment。
最后解码并复核：decode64字母表和填充符只是编码线索；解码成功、结果可读且符合题意，才支持这个假设。形成“原文件 → Comment 原值 → Base64 → 明文”的可复现关系。

如果没有得到预期结果

若签名不是 PNG，就按识别到的格式选工具；若 Comment 为空，应回看其他元数据、结构与尾随数据。严格解码失败时先检查是否复制了标签或漏字符，不把失败解释成“还要再套一层编码”。

逐步命令

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
Get-FileHash -LiteralPath .\01_file\unknown.dat -Algorithm SHA256
finspect type .\01_file\unknown.dat
xxd -g 1 -l 32 .\01_file\unknown.dat
exiftool -a -u -G1 .\01_file\unknown.dat
exiftool -b -Comment .\01_file\unknown.dat
finspect decode64 ZmxhZ3tmaWxlX3R5cGVfYmVmb3JlX2V4dGVuc2lvbn0=

xxd 的 -g 1 按单字节显示，-l 32 只查看前 32 字节。ExifTool 的 -a 保留同名标签，-u 显示未知标签，-G1 显示标签组；-b 输出字段原始值。decode64 只做 Base64 解码。

怎样判读

文件开头为 89 50 4e 47 0d 0a 1a 0a，是 PNG 签名。IHDR 显示宽 256、高 160。Comment 保存了上面的 Base64 字符串。解码结果为：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
flag{file_type_before_extension}

验证与复盘

验证链应写成“PNG 签名 → Comment 原始值 → Base64 解码结果”，不能只提交看到的一段文字。可以将工作副本复制为 out/unknown.png 后打开，说明修改扩展名只是帮助查看，并未恢复或转换数据。

常见误区：看到 .dat 就认定是数据库；对整张二进制图片做 Base64 解码；ExifTool 输出太多时直接搜索 flag，忽略了中间编码字段。你需要记录信息的来源字段和解码步骤。

举一反三

改名为 .zip 后仍应检查内容签名；Comment 不存在时，再按实际结构寻找其他字段或尾部。字段名来自当前输出，不是所有题目的固定入口。

02 · 图片宽度不可信

本题任务

附件为 02_png/broken_width.png。已知只修改了 IHDR 的宽度，原始 IHDR CRC 保留，真实宽度在 1～4096。恢复正确宽度，验证图片结构，再提交 Comment 中的 flag。

解题思路：为什么从这里开始

本题要修复的是尺寸，不是单纯找到文字。题目给出三个约束：只改宽度、旧 CRC 没改、宽度在 1～4096。它们把问题缩成有限范围的验证：枚举候选宽度，找出哪一个能与原 IHDR 校验值相符，而不是凭画面比例猜一个数。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
先定位冲突：xxd 与 pngcheck签名正常只说明解析入口还在；pngcheck 能把异常定位到 IHDR，避免把故障误归于所有图像数据。看到当前宽度与保留的 IHDR CRC 不一致，再依据题设检查宽度。
再明确校验对象：finspect png宽度在 IHDR 数据中以 4 字节大端数保存；CRC 针对块类型和块数据，不针对长度字段或整张文件。明确要替换的字段与计算范围，不能拿整文件 CRC 去比较。
按约束枚举：recover_width.py原 CRC 在本题中是筛选候选的条件。若直接为错误宽度重算一个新 CRC，就丢掉了这个约束。在给定范围得到唯一候选 256；脚本仍保留原 CRC 和其余数据。
用独立检查验收：pngcheck 与尺寸读取CRC 匹配支持的是这组约束下的候选，不自动证明所有块和像素都正确。修复件可解析、尺寸为 256 × 160，必要时再观察图像内容。

如果没有得到预期结果

若候选为零个或多个，应停下来核对题设、字节序、CRC 位置和损坏范围，不能任选一个。若 CRC 已匹配而图像仍无法解码，就继续检查 IDAT 等结构；修复前能读到 Comment 也不等于已经恢复宽度。

逐步命令

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
xxd -g 1 -l 40 .\02_png\broken_width.png
pngcheck -v .\02_png\broken_width.png
finspect png .\02_png\broken_width.png
python .\tools\recover_width.py .\02_png\broken_width.png .\out\fixed_width.png
pngcheck -v .\out\fixed_width.png
exiftool -ImageWidth -ImageHeight -Comment .\out\fixed_width.png

前两项检查出现错误是本题预期行为。恢复脚本只替换宽度，不改高度、不替换原 CRC，也不重新压缩像素。

怎样判读

损坏文件声明为 1 × 160。pngcheck 报告 IHDR CRC 不匹配：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
computed 42379195, expected 6c7b256b
Candidate widths: [256]

候选 256 的 CRC 等于保留值 6c7b256b。修复后 pngcheck 应报告没有检测到错误，ExifTool 显示 256 × 160，Comment 为：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
flag{crc_checks_the_hypothesis}

理解原理与适用条件

将候选宽度打包成 4 字节大端值，放入 IHDR 数据；对 IHDR 类型字节加全部 13 字节数据计算 CRC32，再与文件保存值比较。脚本要求唯一候选，找不到或出现多个时停止，而不是随便选一个。

本题的 Comment 在修复前也能被部分工具读到，因此“读到 flag”不能代替完成宽度恢复。训练目标是验证结构性假设。若题目同时改了高度或 CRC，本脚本的条件不再成立；直接重算 CRC 只能让错误宽度通过某项检查，不能证明图片已恢复。

举一反三

若宽度和 CRC 同时被改，旧 CRC 就不再是独立约束，不能照搬单变量枚举，需要从像素数据或其他证据建立约束。

03 · 安静的图片

本题任务

附件为 03_lsb/quiet.png。已知文字藏在 RGB 图片的 R 通道最低位；像素按从左到右、从上到下读取，每 8 位按高位在前组成字节，遇到零字节结束。恢复信息。

解题思路：为什么从这里开始

题目已经给出了通道、位、扫描顺序和组字节规则，所以下一步是实现并验证这些约定。这里操作的是解码后的像素值，不是把 PNG 压缩文件中的每个字节直接取最低位；两者不是同一层的数据。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
确认输入：尺寸与颜色类型每个 RGB 像素提供一个 R 值；先确认图片能解码，才有可供提取的像素。本题可按 RGB、逐行扫描来取得通道值。
取出比特：每像素计算 R & 1最低位只会使一个通道值改变 0 或 1，解释了为什么肉眼可能看不出差别。每个像素得到一个 0 或 1，八个像素提供一个输出字节。
按约定组字节：左移后加入下一位“先取得的位放在高位”决定了组字节方法；把位序倒转就会得到另一组数据。最前面出现 66 6c 61 67 7b，即可读的 flag{，再按题设的零字节结束规则取文字。
交叉验证：脚本与 zsteg 定向提取比较的是相同通道、相同位、相同遍历和组字节约定下的结果，不是工具名称是否相同。两条路线提取出一致的有效文字，并保留完整提取参数。

如果没有得到预期结果

出现乱码时先逐项核对 R/G/B、bit 0、xy/yx 和字节位序，不立即尝试密码。未知题目可以先枚举参数，但每个可读命中仍需定向提取与上下文验证；本题的结束符也不能当成所有图片隐写的统一规则。

逐步命令

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
exiftool -ImageWidth -ImageHeight -ColorType .\03_lsb\quiet.png
python .\tools\extract_lsb.py .\03_lsb\quiet.png .\out\lsb.bin
xxd -g 1 -l 64 .\out\lsb.bin
strings -n 4 .\out\lsb.bin

脚本依赖的 Pillow 已在工具包中提供。它把像素转为 RGB，逐行读取，连续执行 value = (value << 1) | bit；保存整个提取结果，并在终端输出零字节前的文字。

工具包包含 zsteg 时，还可以用下面两条命令交叉验证：

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
zsteg .\03_lsb\quiet.png
$zs = Join-Path $env:CTF_KIT_ROOT 'runtime\ruby\bin\zsteg'
finspect savebin .\out\zsteg.bin -- ruby.exe $zs -E b1,r,lsb,xy .\03_lsb\quiet.png
strings -n 4 .\out\zsteg.bin

b1 表示每个通道取 1 位，r 表示红通道，lsb 表示取最低有效位，xy 表示逐行扫描。这里的 lsb 指像素位选择，不等于把输出字节倒序。

怎样判读

提取后最前面的字节为 66 6c 61 67 7b，即 ASCII 的 flag{。零字节前的完整文字为：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
flag{one_bit_one_clue}

验证与排错

打开工具包的图像与十六进制实验台，选择 R 通道、位平面 0，可以观察最低位图，但观察图案不能替代读取字节。选 G/B 通道、倒转位序或改变扫描顺序，结果会不同。不要把“换工具”当作改变假设的替代。

该脚本只实现本题约定，不是所有图片隐写的万能提取器。若未知参数，先用 zsteg 列出候选，得到有意义内容后记录完整参数，再执行定向提取。

举一反三

换成 B 通道、按列扫描或相反位序时，必须修改假设并重新提取。记录命中模式，才能在另一张图上重复验证。

04 · 载体里的 ZIP

本题任务

附件为 04_archive/carrier.bin。找到嵌入 ZIP 的起始字节偏移，分离成独立文件，检查完整性后读取答案。

解题思路：为什么从这里开始

载体中出现 PK 03 04，说明那里可能有 ZIP 条目，却不能直接说明它是一个独立、完整的压缩包。解题重点是把“签名命中”推进到“有正确边界且能通过 ZIP 解析与 CRC 校验的对象”。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
扫描候选：finspect scan扫描定位值得查看的字节位置，不负责证明每个命中都是完整文件。得到候选起点，再回到 xxd 核对实际头部与邻近字节。
确定起止：字节偏移与题目结构本题明确是固定前缀加一个到 EOF 的完整 ZIP，才允许从起点一直复制到末尾。确认 512 字节等于 0x200；后续多个本地文件头可以属于同一个 ZIP。
按边界复制：carve.py 或 dd雕刻是复制已确认的范围，不是解密，也不是让工具猜出任意对象的结束位置。得到新的 carved.zip，原载体保持不变，分离方法能被别人复现。
检查目录再测试：7z l → t → x能列目录主要说明元数据可读；解压测试和 CRC 才继续检查条目数据。目录、条目数据和 CRC 均可解析后，再读取 answer.txt。

如果没有得到预期结果

若 7z t 失败，应先查起点、结束范围、是否命中 ZIP 内部条目和是否存在真正加密，不能靠改扩展名宣布成功。真实题未给出 EOF 边界时，要从格式结构确定长度；第二个 PK 03 04 通常也不是第二个完整 ZIP。

逐步命令

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
finspect scan .\04_archive\carrier.bin
xxd -g 1 -s 512 -l 32 .\04_archive\carrier.bin
python .\tools\carve.py .\04_archive\carrier.bin .\out\carved.zip --offset 0x200
7z l .\out\carved.zip
7z t .\out\carved.zip
7z x .\out\carved.zip "-o.\out\carved" -y
Get-Content -LiteralPath .\out\carved\answer.txt

--offset 接受十进制或 0x 十六进制；本题不传 --length 表示从偏移读取到 EOF。7z l 列目录，t 解压测试并校验 CRC，x 保留目录结构解压，-o 后紧接目标目录，-y 自动同意覆盖已有输出。

Linux 或包内 BusyBox 的等价字节复制命令：

Kali Linux · Bash从 labs 运行；先完成对应系统的环境准备
dd if=04_archive/carrier.bin of=out/carved_dd.zip bs=1 skip=512

bs=1 表示每个块是 1 字节，所以 skip=512 才是跳过 512 字节。若 bs=512、skip=512，将跳过 262144 字节。

怎样判读

扫描在十进制 512 / 十六进制 0x200 发现第一个 ZIP 本地文件头。后续在 0x254 发现另一个本地文件头，在 0x2a4、0x2dc 发现中央目录，在 0x314 发现目录结束记录；它们属于同一个 ZIP。

7z t 应显示 Everything is Ok。answer.txt 内容为：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
flag{offsets_make_carving_repeatable}

验证与排错

直接用 7-Zip 打开带前缀的载体，有时也会成功；本题仍要求记录偏移和分离方法。不要把第二个本地文件头误认为第二个独立压缩包。真实题如果含多个对象或尾随数据，应结合格式长度确定结束位置，不能一律截到文件末尾。

举一反三

若 ZIP 后面还有其他附件，应先确定 ZIP 结束位置再设置提取长度。本题“从 0x200 到末尾”的范围不适用于所有载体。

05 · 已删除的文本

本题任务

附件为 05_disk/tiny_fat16.dd，约 9 MiB。定位 FAT16 分区，列出已删除的文件，导出其内容并说明恢复依据。

解题思路：为什么从这里开始

这道题包含两个层次：先找到文件系统位于镜像的哪里，再判断删除项的数据是否仍可恢复。若偏移错了，后面的文件列表和恢复都没有可靠基础；若只看见删除标记，也还不能断言内容一定完整。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
定位文件系统：mmls整盘镜像可能先有分区表，FAT 引导扇区不一定在镜像起点。从当前输出取得分区起始扇区；本题是每扇区 512 字节、起点 2048。
列目录：fls，再加 -d先看整体目录，再收窄到删除项，才能理解星号、名称与元数据编号分别表示什么。本题删除项的元数据编号为 4；它不是文件起始簇号，也不是分区偏移。
按对象恢复：icat -r目录项可能还保留大小和起始簇，数据区也可能尚未被覆盖；icat 根据这些结构尝试读取内容。以本次编号和同一 -o 起点导出字节，避免将整盘位置与分区内部位置混用。
复核恢复条件：结构脚本与哈希本题有未覆盖、单簇和未碎片化等简化条件，可用结构读取结果检查工具导出的字节是否一致。两种方法的内容与 SHA256 相同，再说明恢复成立的具体条件。

如果没有得到预期结果

mmls 没有分区表结果时，不应直接认定镜像坏了；它也可能本来就是裸文件系统，应在偏移 0 用 fsstat 验证。找到删除项却读不到完整内容时，要考虑簇重用、碎片与覆盖，不能把样本中“可恢复”的结果推广到所有删除文件。

逐步命令

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
mmls .\05_disk\tiny_fat16.dd
fls -r -o 2048 .\05_disk\tiny_fat16.dd
fls -r -d -o 2048 .\05_disk\tiny_fat16.dd
finspect savebin .\out\recovered.txt -- icat.exe -r -o 2048 .\05_disk\tiny_fat16.dd 4
Get-Content -LiteralPath .\out\recovered.txt
python .\tools\read_training_fat.py .\05_disk\tiny_fat16.dd .\out\recovered_by_structure.txt
Get-FileHash -LiteralPath .\out\recovered.txt, .\out\recovered_by_structure.txt -Algorithm SHA256

mmls 显示每扇区为 512 字节，DOS FAT16 分区起点为 2048，所以分区的字节偏移是 2048 × 512 = 1048576。-o 使用扇区数，不能传 1048576。

fls 的 -r 递归列目录，-d 仅列删除项；icat 的 -r 启用删除项恢复处理。两者选项的含义应分别理解。finspect savebin 直接保存 icat.exe 的原始 stdout，避免 PowerShell 文本重编码。

怎样判读

包内 TSK 4.14.0 的 fls 输出：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
r/r * 4:  _ECRET.TXT

星号表示删除项，4 是本次输出的元数据编号，_ECRET.TXT 的首字符已经丢失。不要把 4 与起始簇 3 混淆。导出内容：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
flag{deleted_entry_is_a_clue}

两种导出方法生成的字节和 SHA256 应相同。本样本中删除目录项首字节为 E5；原起始簇号为 3、大小字段仍在；FAT 中该簇标记空闲，但实际内容没有被覆盖。

验证与排错

read_training_fat.py 只解析本课单分区、单簇、未碎片化的样本，不能作为通用 FAT 恢复器。真实环境存在簇重用和碎片，可能只能部分恢复。换镜像后必须使用新输出的元数据编号，不能照抄 4。

如使用 Autopsy：New Case → Add Data Source → Disk Image or VM File → 选择镜像 → 浏览已删除文件 → 选中文件后 Extract。Autopsy 为选装 GUI；本题的完整操作和验证已可由包内 TSK 完成。

举一反三

分区起点变化时，fls 与 icat 的 -o 要一起更新；元数据编号也要从新的 fls 输出获取，不能继续照填 4。

06 · 界面里消失的记录

本题任务

附件为 06_sqlite/case.db。应用界面里某条记录“已删除”，请找到其原始内容，判断这里属于哪一种删除。

解题思路：为什么从这里开始

界面中“看不见”不等于数据库中“已物理移除”。先检查普通表里是否仍有目标行，是成本较低且可直接验证的假设。只有明确正常表查询不能回答问题，才有理由继续考虑 WAL、空闲页或物理记录恢复。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
确认格式与表名扩展名只是线索；识别 SQLite 后列出实际表名，避免照抄别题的表名和 SQL。本库中存在 artifacts 表，才进一步查看它的结构。
读字段：.schema 与 PRAGMA先知道 id、name、deleted、note 各自如何保存，才能写出有依据的筛选条件。发现普通表中存在 deleted 标记；字段名提示业务含义，但还需看实际取值和行。
先看完整行，再筛 deleted=1查看所有字段和取值，可以验证“隐藏记录仍在表中”的假设，避免条件写反或把别的状态误当删除。目标行能被正常 SELECT 读出，其 deleted 为 1，note 中仍有内容。
用只读连接和另一种入口复核SQLite CLI 与标准库脚本应得到同一行；这里验证的是查询和内容，不是底层页恢复能力。据此归类为业务软删除，不需要通过 .recover 才能完成本题。

如果没有得到预期结果

若正常表里找不到目标行，应重新核对数据库快照、表和业务条件；不能反过来证明“记录从未存在”。需要检查 WAL 时保留同一快照的配套文件，另行分析；不要为找数据在原库上执行更新或 VACUUM。

逐步命令

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
finspect type .\06_sqlite\case.db
sqlite3 -readonly .\06_sqlite\case.db ".tables"
sqlite3 -readonly .\06_sqlite\case.db ".schema artifacts"
sqlite3 -readonly .\06_sqlite\case.db "PRAGMA table_info(artifacts);"
sqlite3 -readonly -header -column .\06_sqlite\case.db "SELECT id,name,deleted,note FROM artifacts ORDER BY id;"
sqlite3 -readonly -header -column .\06_sqlite\case.db "SELECT id,name,note FROM artifacts WHERE deleted=1;"
python .\tools\query_case.py .\06_sqlite\case.db

-readonly 禁止本次连接写数据库；-header 显示列名，-column 对齐文本。.tables/.schema 是 sqlite3 的点命令，SELECT/PRAGMA 是 SQL，点命令通常独占一行。双引号包住整条 SQL，单引号用于 SQL 字符串字面量。

怎样判读

artifacts 的列为 id、name、deleted、note。记录 id=2，name=old-note，deleted=1，其 note 为：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
flag{query_the_schema_first}

这是业务软删除：记录仍然存在于普通查询可见的表中。题目不需要十六进制恢复，也不需要 .recover。

验证与延伸

使用 SQLite CLI 与标准库脚本得到相同行可交叉验证。实际取证遇到 WAL 模式时，应同时保留同一快照中的 db、db-wal、db-shm，先复制再解析；不能把任意时刻的文件拼在一起。WAL 可能保留尚未检查点的数据，也可能已被复用，不能保证其中必有历史记录。

举一反三

deleted=1 的行仍能直接 SELECT 时，先解释业务字段如何控制显示；有物理删除及残留证据后再考虑页级恢复。

07 · 谁完成了下载

本题任务

附件为 07_logs/access.log 和 audit.jsonl。确定账号 trainee 成功下载 case_notes.zip 的来源 IP 和 UTC+8 完成时间，按 flag{IP_HHMMSS} 提交。

解题思路：为什么从这里开始

题目要求的是“哪个账号对哪个文件完成下载、来源 IP 是什么、何时完成”。单个状态码或一条登录记录都回答不完这些问题。先从审计日志找符合账号、文件名和完成事件的记录，再用同一次请求的标识关联访问日志，最后统一时间。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
先筛业务事件：账号、文件名、download_completed题目问完成，所以先区别 export_started 与 download_completed，而不是先挑一个 200 或时间相近的请求。在审计日志第 4 行找到目标完成事件及其 request_id=r-103。
再关联请求：request_id 对 rid两份日志写入顺序可能不同，相邻行没有天然对应关系；同一次请求的键比“时间差不多”更可靠。访问日志第 7 行的 rid=r-103 与目标事件相连，记录下载请求和来源 IP。
检查身份、对象与状态是否一致登录事件只能辅助身份背景；HTTP 202 只表示已接受，200 也不单独证明某个账号完成了目标业务。本题同时核对 trainee、object_id=42、case_notes.zip、完成事件和发送字节数。
最后做带时区的时间转换时间结尾 Z 表示 UTC；只有明确来源时区和目标 UTC+8，才有依据进行换算。01:18:31Z 对应 09:18:31+08:00，按题目格式组成 HHMMSS。

如果没有得到预期结果

缺少 request_id 等稳定键时，应补充 session_id、对象和时间范围等关联依据，并写明仍有歧义，不能按行号硬配。若时间没有时区，也不能默认加 8；这里归属的是样本账号的事件，不等于证明某个现实人物亲自操作。

逐步命令

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
Select-String -Path .\07_logs\audit.jsonl -Pattern 'case_notes.zip'
Select-String -Path .\07_logs\audit.jsonl -Pattern 'download_completed'
Select-String -Path .\07_logs\access.log -Pattern 'r-101|r-102|r-103'
python .\tools\timeline.py .\07_logs\audit.jsonl
Get-Content .\07_logs\audit.jsonl | ForEach-Object { $_ | ConvertFrom-Json } | Where-Object { $_.event -eq 'download_completed' } | Format-List *

Select-String 默认将 | 作为正则的“或”；若需要找字面值可加 -SimpleMatch。ConvertFrom-Json 按字段解析，避免用空格切割 JSON。时间转换脚本明确使用带时区时间，不依赖学员电脑所在时区。

怎样判读

证据行号关联键结论
access.log3r-101登录请求，来源 192.0.2.44
audit.jsonl1r-101trainee 登录成功
access.log6r-102导出请求返回 202，只表示已接受
audit.jsonl3r-102export_started，object_id=42
access.log7r-103下载返回 200，发送 2048 字节
audit.jsonl4r-103download_completed，文件 case_notes.zip

完成时间为 2026-10-18T01:18:31Z，即 2026-10-18 09:18:31+08:00。来源 IP 为 192.0.2.44，最终答案：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
flag{192.0.2.44_091831}

验证与复盘

结论同时有请求、身份、文件对象、事件状态和时间支持。不要把返回 202 的 09:18:30 当成完成时间，也不能只凭 200 就断定具体业务行为。样本 IP 是文档专用地址，日志为本地合成数据。

举一反三

开始与完成跨日时，应换算完成事件的完整日期时间；只对小时数加 8 而忽略跨日可能提交错误答案。

08 · 公开题复现：Glory of the Garden

本题任务与来源

原题为 picoCTF 2019 的 Glory of the Garden，平台入口：https://play.picoctf.org/practice/challenge/44 。本包 public_examples/garden_demo.jpg 是自制复现，模拟“图片中有可读隐藏文本”的基础考点。

解题思路：为什么从这里开始

图片能正常打开，只能说明解码器可以显示图像，不能说明文件里的每个字节都参与了显示。本题先检验一个成本很低的假设：答案是否直接以可打印文本存在于文件中。命中之后还要定位原始位置，才能解释为什么它没有显示在画面里。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
先识别格式，再用 strings 查文本strings 直接扫描文件字节，不依赖 JPEG 解码器；对于未加密的附加文字，比尝试像素隐写更直接。确认实际是 JPEG，并在可打印序列中找到完整 flag，而不是只看到零散的 flag 字样。
保留字节偏移，而不只记命中行号grep -n 标的是 strings 输出的行号，不能拿来作为 xxd 的源文件偏移。GNU strings -t x 或本包 finspect strings 可报告输入中的字节位置。在原始字节视图找到同一段文字及相邻字节，证明它确实来自该附件。
判断文字属于哪一部分元数据、压缩图像数据和文件尾部文本需要不同的解释；仅凭字符串命中还无法认定藏匿方式。本题自制 JPEG 的文字在实际图像结束标记 FF D9 之后；这说明它是尾部附加文本。
复核答案与样本身份同考点复现保留的是方法，不是官方文件的每个字节或官方 flag。提交本地 garden_demo.jpg 的结果、实际位置与上下文，并明确使用的是自制复现附件。

如果没有得到预期结果

没搜到文本只说明当前长度阈值、编码与输入范围下没有命中，不等于图片没有信息。下一步可查元数据、尾部结构或其他编码。不要把任意一个 FF D9 字节序列直接当作真实结束位置；应结合 JPEG 结构确认。

逐步命令

strings -n 4 .\public_examples\garden_demo.jpg | grep -n 'flag{'
finspect strings .\public_examples\garden_demo.jpg -n 8

strings 输出连续可打印字符串，-n 4 指定最少 4 字符；grep -n 给的是 strings 输出的行号，不是图片的字节偏移。要定位原文件位置，使用 finspect strings 的 0x 偏移。

怎样判读与验证

本复现的 JPEG 图像结束标志 FF D9 后追加了教学文本，包含：

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
flag{strings_see_more_than_pixels}

先读出文字，再用实验台十六进制搜索或 xxd -s 指定偏移核对其位置。图像正常显示只说明解码器能读像素，不说明文件没有额外数据。本题无需 LSB 或口令。

原件与复现的图像、哈希、答案不同。若改用官方附件，应以实际读到的 picoCTF{...} 为准，不能将这里的 flag 作为原题答案。

举一反三

字符串位于 XMP 块时，应解释为元数据存储；即使 strings 都能命中，藏匿位置的结论也要跟着实际字节改变。

原题为 picoCTF 2021 的 information，平台入口：https://play.picoctf.org/practice/challenge/186 。本包 public_examples/cat_demo.jpg 自制复现了“XMP License 中保存 Base64”的基础考点。

如换用官方附件，字段值与 flag 后缀以原件为准。公开题引用说明见练习材料中的 public_examples/SOURCES.md。

10 · 补充练习：只修复 PNG 文件头

本题任务

02_png/broken_header.png 无法作为 PNG 打开。已知只损坏了最前 8 字节，其余块内容保持不变。修复签名并验证，good.png 是对照件。

解题思路：为什么从这里开始

真实 RAM 选择 memmap --dump要找编辑文字，应检查可读进程映射页；pslist --dump 导出的可执行映像主要用于程序本体分析，不能覆盖所有编辑缓冲区。保留当前镜像的映射表与实际导出文件列表，再对导出结果检索。
ASCII 与 UTF-16LE 分别检查66 00 6c 00 61 00 67 00 这样的交替零字节会打断普通 ASCII 连续串；每两个字节组成一个小端编码单元。UTF-16LE 路线找到完整 flag，而 ASCII 无结果本身不能否定文本存在。
把字符串起点换算成 flag 起点并核对字节整段宽字符串起点与其中子串起点不同，工具结果必须明确坐标系。本题字符串从 0x100 开始，前缀 14 个字符占 28 字节，所以 flag 位于 0x11c；用 xxd 检查该处原字节。

如果没有得到预期结果

两种编码都无命中时，考虑检索词、输入范围、缺页、换出、覆盖或其他编码，并写明未能恢复，不等于从未输入。0x11c 只属于本题片段；映射回进程虚拟地址或原 RAM 偏移需实际映射关系，不能直接照抄这个数值。
