06 / 二进制基础：字节、十六进制与偏移

1 字节等于 8 位。十六进制用 0～9、a～f 表示数值，每两位十六进制表示一个字节。0x200 是十六进制偏移，换算为十进制是 512。

偏移从 0 开始。文件偏移 16 指第 17 个字节。Python 切片 data[16:20] 取偏移 16、17、18、19 的四字节，不包含 20。

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
xxd -g 1 -l 32 .\01_file\unknown.dat
xxd -g 1 -s 0x10 -l 16 .\01_file\unknown.dat
Kali Linux · Bash从 labs 运行；先完成对应系统的环境准备
xxd -g 1 -l 32 ./01_file/unknown.dat
xxd -g 1 -s 0x10 -l 16 ./01_file/unknown.dat

上面两组都使用 xxd：-g 1 按单字节分组，-l 限制显示长度，-s 跳到指定字节偏移。Windows 使用包内 BusyBox xxd，Kali 使用其原生命令。这些共同选项在两条路线中都适用。

十六进制视图通常分三列：左边是字节偏移，中间是原始字节，右边是可打印字符。右边的点通常表示该字节没有直接显示为可打印 ASCII，不能据此认定原始内容就是“点”。

PNG 签名为 89 50 4e 47 0d 0a 1a 0a。扩展名可随意改，签名和内部结构更接近内容证据；发现签名后仍须检查对应结构，避免把偶然字节当成完整对象。

07 / 先保留输入，再验证副本

哈希把任意长度输入映射为固定长度摘要。SHA256 相同可用于核对课堂副本的一致性；哈希不是文件内容的“解码方式”，不能从摘要还原文件。

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
New-Item -ItemType Directory -Force -Path .\out\work | Out-Null
Get-FileHash -LiteralPath .\01_file\unknown.dat -Algorithm SHA256
Copy-Item -LiteralPath .\01_file\unknown.dat -Destination .\out\work\unknown.dat
Get-FileHash -LiteralPath .\out\work\unknown.dat -Algorithm SHA256
Kali Linux · Bash从 labs 运行；先完成对应系统的环境准备
mkdir -p out/work
sha256sum ./01_file/unknown.dat
cp -- ./01_file/unknown.dat ./out/work/unknown.dat
sha256sum ./out/work/unknown.dat

两次摘要应相同。修复、提取、解压会产生新文件，新文件摘要不同是正常现象；记录它对应哪一步输出。输入哈希清单在 labs/SHA256SUMS.txt。

08 / file、ExifTool 与字符串：各自回答什么

工具适合回答的问题不能直接得出的结论
file / finspect type文件可能是什么格式单凭命中不能证明整个文件完整
xxd / 文件观察实验台指定偏移到底有哪些字节不能仅凭局部文字决定文件的所有语义
strings / finspect strings哪些位置存在连续可读文字命中不自动说明来源、时间或所属进程
ExifTool元数据字段及字段组是什么没有元数据不等于没有隐藏信息

Windows 用 finspect 识别本课常见签名；它是附源码的教学助手，不是完整 libmagic：

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备

finspect strings .\01_file\unknown.dat --encoding ascii

Kali Linux · Bash从 labs 运行；先完成对应系统的环境准备

exiftool -a -u -G1 ./01_file/unknown.dat

GNU strings 的 -a 扫描整个输入，-t x 显示十六进制字节偏移，-n 4 指定最小长度。ExifTool 的 -a 保留同名字段，-u 显示未知字段，-G1 显示字段组，-b 定向输出原始值。先找到字段，再只提取它的值，可以避免把标签名一起送去解码。

09 / 编码、加密、哈希与端序

概念是否用于隐藏秘密常见例子在取证中的用途
编码通常没有秘密密钥Base64、Hex、URL 编码把文本或二进制换一种表示

端序决定多个字节如何组成整数。00 00 01 00 按大端解释是 256；按小端解释是 65536。PNG 的宽高用大端，FAT16 目录字段多为小端，必须按格式文档解释，不能因为“看起来像一个数”就决定含义。

10 / PNG 结构与 CRC：修复为什么需要依据

PNG 从 8 字节签名开始，之后每个块通常由“长度 4 字节 → 类型 4 字节 → 数据 → CRC 4 字节”组成。IHDR 数据长 13 字节，含宽、高、位深、颜色类型等；宽在文件偏移 16～19，高在 20～23。

PNG 块的 CRC32 覆盖“类型 + 数据”，不含块长度。保存的 CRC 与重算值不同说明存在矛盾，但不能单凭矛盾确定是哪一项被改动。

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备
pngcheck -v .\02_png\broken_width.png
finspect png .\02_png\broken_width.png
Kali Linux · Bash从 labs 运行；先完成对应系统的环境准备
pngcheck -v ./02_png/broken_width.png
python3 ./tools/finspect.py png ./02_png/broken_width.png

练习样本的错误是故意设置的。你需要读出“哪个块、预期值、计算值”，再决定修复方向。第 2 题已明确只改宽度且原 CRC 保留，因此可以用 CRC 约束枚举候选。若直接替换 CRC，只是让错误的尺寸得到新校验，不能证明恢复了原图。

11 / LSB：一个像素位怎样组成文字

RGB 像素有红、绿、蓝三个通道，8 位通道的数值范围为 0～255。最低有效位是最右边一位：120 的最低位为 0，121 的最低位为 1。只改变这一位，颜色差通常很小。

提取之前要固定四个条件：选哪个通道、每个通道取几位、像素遍历顺序、这些位如何组成输出字节。第 3 题约定 R 通道最低位、逐行扫描，每 8 位按高位在前组成字节。

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
取出的位：0 1 1 0 0 1 1 0
按高位在前组成：01100110₂ = 0x66 = ASCII f

用文件观察实验台选择 R 通道与位平面 0，能观察最低位变化；位平面图不是已解码文字。还需要按题目约定组合字节。

Windows 的 zsteg 启动器自动加 --no-file，关闭外部 Unix file 调用，内置文本扫描与定向提取仍可用。Kali 可以使用其原生 file 配合 zsteg：

Windows · PowerShell从 labs 运行；先完成对应系统的环境准备

python .\tools\extract_lsb.py .\03_lsb\quiet.png .\out\lsb.bin
Kali Linux · Bash从 labs 运行；先完成对应系统的环境准备

zsteg 的 b1,r,lsb,xy 表示取 1 位、红通道、最低有效位、逐行扫描。这里的 lsb 是选择像素位，不能直接等同于把输出字节逆序。

7z x ./04_archive/locked.zip -ptraining2026 -o./out/zip_example -y

-o 后紧接路径。Windows PowerShell 中将整个“-o路径”用引号包住，尤其是点路径或含空格的路径。这里的口令是公开的教学值，实际解题先从提示构造小字典，再验证解密结果。

ZIP 本地头通常以 PK 03 04 开始，中央目录和结束记录还有各自的签名。同一个 ZIP 可以有多个本地文件头，不能把每个 PK 都当作独立压缩包。

文件雕刻指根据边界把对象字节复制出来。签名命中只是候选；应确定起点、结束边界和完整性。第 4 题属于“固定前缀 + 单个 ZIP 到 EOF”；别把这个特定条件推广到所有文件。

“加密位被错误设置”与“真实加密”不同。清除 ZIP 标志不是解密，只在内容本来就未加密时才可能修正声明；需要同时验证解压和 CRC。第 11、12 个案例会分别练习。

13 / 磁盘与 SQLite：先识别结构，再提取

案例 01 · 没有扩展名的图片

本题任务

附件为 01_file/unknown.dat。识别它的真实格式，找到隐藏信息并提交 flag，同时说明编码值来自哪里。

解题思路：为什么从这里开始

题目先问“真实格式”，因此第一步要验证文件内容，不能由 .dat 猜用途。确认 PNG 后，优先检查格式本来就能保存的文字字段；这比没有线索地枚举隐写参数更直接。只有在 Comment 中实际发现可疑编码值后，才提出“它可能是 Base64”的假设。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
先识别格式：finspect type 与 xxd识别器给出候选，十六进制视图让你亲眼核对签名；改后缀不会改变字节。开头符合 PNG 签名，后面还有可解析的 IHDR，才沿图片路线继续。
再读元数据：exiftool -a -u -G1PNG 不只保存像素，还能包含文本。先查看字段组、字段名和原值，避免漏掉经过编码的线索。发现 Comment 中的长串，而不是假定“任意长串都是答案”。
定向提取：exiftool -b -Comment这一条只取字段值，避免将标签名、冒号等显示文字混入解码输入。得到完整原串，保留其来源为此文件的 Comment。
最后解码并复核：decode64字母表和填充符只是编码线索；解码成功、结果可读且符合题意，才支持这个假设。形成“原文件 → Comment 原值 → Base64 → 明文”的可复现关系。

如果没有得到预期结果

若签名不是 PNG，就按识别到的格式选工具；若 Comment 为空，应回看其他元数据、结构与尾随数据。严格解码失败时先检查是否复制了标签或漏字符，不把失败解释成“还要再套一层编码”。

逐步命令

案例 02 · 图片宽度不可信

本题任务

解题思路：为什么从这里开始

本题要修复的是尺寸，不是单纯找到文字。题目给出三个约束：只改宽度、旧 CRC 没改、宽度在 1～4096。它们把问题缩成有限范围的验证：枚举候选宽度，找出哪一个能与原 IHDR 校验值相符，而不是凭画面比例猜一个数。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
先定位冲突：xxd 与 pngcheck签名正常只说明解析入口还在；pngcheck 能把异常定位到 IHDR，避免把故障误归于所有图像数据。看到当前宽度与保留的 IHDR CRC 不一致，再依据题设检查宽度。

解题思路：为什么从这里开始

载体中出现 PK 03 04，说明那里可能有 ZIP 条目，却不能直接说明它是一个独立、完整的压缩包。解题重点是把“签名命中”推进到“有正确边界且能通过 ZIP 解析与 CRC 校验的对象”。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
扫描候选：finspect scan扫描定位值得查看的字节位置，不负责证明每个命中都是完整文件。得到候选起点，再回到 xxd 核对实际头部与邻近字节。
确定起止：字节偏移与题目结构本题明确是固定前缀加一个到 EOF 的完整 ZIP，才允许从起点一直复制到末尾。确认 512 字节等于 0x200；后续多个本地文件头可以属于同一个 ZIP。

案例 05 · 已删除的文本

本题任务

附件为 05_disk/tiny_fat16.dd，约 9 MiB。定位 FAT16 分区，列出已删除的文件，导出其内容并说明恢复依据。

解题思路：为什么从这里开始

这道题包含两个层次：先找到文件系统位于镜像的哪里，再判断删除项的数据是否仍可恢复。若偏移错了，后面的文件列表和恢复都没有可靠基础；若只看见删除标记，也还不能断言内容一定完整。

每一步在验证什么

要回答的问题选择这一步的理由看到什么才继续
定位文件系统：mmls整盘镜像可能先有分区表，FAT 引导扇区不一定在镜像起点。从当前输出取得分区起始扇区；本题是每扇区 512 字节、起点 2048。
列目录：fls，再加 -d先看整体目录，再收窄到删除项，才能理解星号、名称与元数据编号分别表示什么。本题删除项的元数据编号为 4；它不是文件起始簇号，也不是分区偏移。
按对象恢复：icat -r目录项可能还保留大小和起始簇，数据区也可能尚未被覆盖；icat 根据这些结构尝试读取内容。以本次编号和同一 -o 起点导出字节，避免将整盘位置与分区内部位置混用。
复核恢复条件：结构脚本与哈希本题有未覆盖、单簇和未碎片化等简化条件，可用结构读取结果检查工具导出的字节是否一致。两种方法的内容与 SHA256 相同，再说明恢复成立的具体条件。

如果没有得到预期结果

mmls 没有分区表结果时，不应直接认定镜像坏了；它也可能本来就是裸文件系统，应在偏移 0 用 fsstat 验证。找到删除项却读不到完整内容时，要考虑簇重用、碎片与覆盖，不能把样本中“可恢复”的结果推广到所有删除文件。

Get-Content -LiteralPath .\out\recovered.txt
python .\tools\read_training_fat.py .\05_disk\tiny_fat16.dd .\out\recovered_by_structure.txt
Get-FileHash -LiteralPath .\out\recovered.txt, .\out\recovered_by_structure.txt -Algorithm SHA256
Kali Linux · Bash从 labs 运行；先完成对应系统的环境准备

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
flag{deleted_entry_is_a_clue}

把字符串起点换算成 flag 起点并核对字节整段宽字符串起点与其中子串起点不同，工具结果必须明确坐标系。本题字符串从 0x100 开始，前缀 14 个字符占 28 字节，所以 flag 位于 0x11c；用 xxd 检查该处原字节。

如果没有得到预期结果

两种编码都无命中时，考虑检索词、输入范围、缺页、换出、覆盖或其他编码，并写明未能恢复，不等于从未输入。0x11c 只属于本题片段；映射回进程虚拟地址或原 RAM 偏移需实际映射关系，不能直接照抄这个数值。

示例输出 / 数据 · 不执行用于比较与判读，无需输入终端
offset-in-input = 0x11c
flag{utf16_is_still_text}

0x11c 为十进制 284，含义仅是“该模拟输入文件中的字节偏移”，不是原始 RAM 物理偏移，也不是进程虚拟地址。 finspect 先打印整段可打印宽字符串的起点 0x100；其中前缀“Unsaved note: ”占 28 字节，所以 flag 从 0x11c 开始。search_excerpt.py 定向匹配 flag 并报告其准确起点。

换成真实 RAM 后的 Vol3 顺序

先完成 info、pslist、pstree、cmdline，确认目标 PID，再导出进程映射页：

Windows · PowerShell从 labs 运行 · 需要另备真实 RAM
New-Item -ItemType Directory -Force -Path .\out\proc | Out-Null
python $v3 -f $img -o .\out\proc windows.memmap --pid 2460 --dump

finspect strings .\out\proc\pid.2460.dmp --encoding ascii

Kali Linux · Bash从 labs 运行 · 需要另备真实 RAM
mkdir -p out/proc
vol -f "$img" -o out/proc windows.memmap --pid 2460 --dump
ls -l out/proc
strings -a -t x out/proc/pid.2460.dmp | grep 'flag{'
strings -a -e l -t x out/proc/pid.2460.dmp | grep 'flag{'

导出文件名须先以实际列表为准。memmap --dump 导出可访问的进程映射页；pslist --dump 侧重进程可执行映像，不能把两者混用来证明记事本文档文字不存在。

自检与排错

先解释为什么 cmdline 无路径仍值得查看进程内存：文本可能尚未保存，也可能只存在于缓冲区。再说明为何检索无结果不等于未出现过：页可能缺失、被换出、编码不同或已经覆盖。

如需把导出偏移映射回虚拟地址，应保存 memmap 映射表，按实际导出段和地址对应关系换算；本例没有这份真实映射，不做推断。

举一反三

命中导出文件第 N 个字节时，先查导出映射再讨论虚拟地址；原镜像偏移、导出偏移与进程地址不是同一坐标。
